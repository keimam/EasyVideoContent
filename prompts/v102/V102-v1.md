## Butir

### B1 — Coverr: berhenti setelah 401/403 pertama
Fakta dari kode saat ini:
- `stock.py` memanggil `material.search_videos_coverr` (upstream, timeout `(30, 60)`).
- Saat 403, fungsi itu mengembalikan `[]`, jadi 403 tidak bisa dibedakan dari "tidak ada hasil".
- Di `service.py:_search_single_provider_tiers`, `err_txt` untuk Coverr kosong. Akibatnya Coverr dicoba lagi di setiap shot (±40 s terbuang; 45/46 request ditolak di uji A2).

Kerjakan:
1. Buat pencarian Coverr milik longform (mis. `visual/coverr_client.py`). Endpoint dan parameternya sama dengan upstream (`/videos`, `urls=true`, `filter=is_vertical:false`, `page_size`, `sort=popular`). Timeout memakai nilai B3 (bukan 30/60). Hasilnya dipetakan ke field `VisualCandidate` yang sama persis dengan sekarang (`candidate_id=coverr_<id>`, license, rendition, `source_info`).
2. Bila respons 401/403: tandai Coverr `auth_blocked` di status sumber tingkat proses. Lewati Coverr untuk **seluruh sisa run** tanpa request baru. Status ini direset saat key Coverr berubah atau aplikasi dimulai ulang. Ini bukan dimatikan permanen; patuhi keputusan desain handover §7.
3. 429/5xx/timeout memakai pemutus yang sudah ada (`free_providers`) atau logika setara. Jangan buat versi kedua yang berbeda perilaku.
4. Jangan pernah GET `mp4_download` saat pencarian. Coverr menghitung GET itu sebagai satu download, jadi URL itu hanya diambil saat aset benar-benar diunduh.
5. Tes: 403 pada shot 1 → shot 2..N tidak memanggil HTTP Coverr sama sekali (hitung panggilan mock), dan status sumber = `auth_blocked`.

### B2 — Sumber yang dilewati harus terlihat di langkah Visual
Saat ini sumber yang error atau sedang cooldown hanya muncul di expander per shot (`components.py` ±3621). Kerjakan:
1. Kumpulkan ringkasan per sumber selama fetch: `ok`, `cooldown` (berapa kali), `auth_blocked`, `timeout`, error terakhir (sudah diredaksi, maks. 120 karakter). Simpan sebagai `source_status` di `visual_metrics.json`.
2. Di langkah Visual, setelah fetch selesai (dekat banner "Selesai dalam …"), tampilkan satu kotak peringatan bila ada sumber tidak sehat. Contoh: "Coverr dilewati: API key ditolak (403). Cek key di API & Penyedia AI." dan "Openverse dijeda 2× karena server lambat (504)." Teks ada di i18n id + en.
3. Tes: unit untuk agregasi `source_status`, dan satu AppTest/unit render yang membuktikan peringatan muncul untuk `auth_blocked`.

### B3 — Timeout dan pemutus bisa diatur (koneksi lambat)
Saat ini `_http_get(timeout=6)`, `_TRANSIENT_FAILURE_THRESHOLD = 2`, `_TRANSIENT_COOLDOWN_SECONDS = 120` di-hardcode. Kerjakan:
1. Tambah pengaturan longform `network_profile`: `normal` (default; timeout 6 s, ambang 2, jeda 120 s) dan `lambat` (timeout 15 s, ambang 3, jeda 60 s). Simpan di config longform, dengan nilai default bila kunci tidak ada.
2. Tambah pilihan di Settings studio (lewat hook `render_settings_studio_controls` yang sudah ada, tanpa mengubah `Main.py`).
3. Semua sumber gratis + Coverr (B1) membaca profil ini.
4. Tes: profil `lambat` → timeout yang diteruskan ke `requests.get` = 15, dan cooldown baru aktif setelah gagal ke-3.

### B4 — Thread paralel: kembali ke spesifikasi ≤4
`service.py:_run_parallel_phase` memakai `min(6, len(phase_slices))`, padahal spesifikasi ≤4 dan deviasi ini tidak pernah dilaporkan.
1. Ganti dengan konstanta bernama `MAX_PARALLEL_SOURCES = 4` di modul visual. Laporkan bila ada alasan kuat untuk nilai lain (dengan angka benchmark nyata, bukan perkiraan).
2. Tes: dengan 6 sumber aktif, `ThreadPoolExecutor` dibuat dengan `max_workers == 4`.
3. Catat waktu fetch proyek uji (pakai proyek Yuki-onna bila tersedia, atau sebutkan proyek yang dipakai) sebelum dan sesudah, dari `visual_metrics.json`.

### B5 — API key gambar per preset
Saat ini hanya ada satu `openai_image_api_keys` untuk Together, DeepInfra, dan Custom. `apply_image_provider_preset` mempertahankan key itu, sehingga key Together terpakai di DeepInfra.
1. Tambah `openai_image_api_keys_by_preset` (dict `preset_key → key`) di config.
2. Saat preset diterapkan: simpan key aktif ke preset lama, lalu muat key preset baru ke `openai_image_api_keys` (kunci ini tetap dibaca upstream `material.py`, jadi upstream tidak diubah). Bila preset baru belum punya key, kolom dikosongkan, bukan diisi key preset lain.
3. Migrasi sekali: key tunggal yang sudah ada dimasukkan ke preset hasil `infer_image_preset_key(base_url)` saat ini. Tidak ada key yang hilang.
4. Tetap patuhi "tidak ada key bawaan" dan "preset tidak menimpa key pengguna": key pengguna dipindah, tidak pernah dibuang.
5. Tes: (a) isi key Together → pindah ke DeepInfra → kolom kosong → kembali ke Together → key Together kembali; (b) migrasi config lama tanpa dict; (c) `redact_api_secrets` tetap menyamarkan key di pesan Uji 1 gambar.
