## A1.1 — Bedakan "key ditolak" dari "403 di tengah jalan" (Coverr)
Temuan dari Final Report V102-v1 §5: Coverr menjawab **56× HTTP 200 lalu 1× 403**, dan `coverr_client._on_auth_fail` langsung memblokir Coverr untuk seluruh sisa proses dengan pesan "API key ditolak". Key yang sudah 56× berhasil hampir pasti bukan key yang salah. 403 seperti ini lebih mungkin batas pemakaian atau penolakan sementara.

Kerjakan:
1. Lacak per proses apakah key Coverr saat ini (pakai `key_hash`) **pernah berhasil** (HTTP 200).
2. Aturan baru:
   - **401** kapan pun → `auth_blocked` (perilaku sekarang).
   - **403 sebelum ada satu pun 200** untuk key ini → `auth_blocked` (perilaku sekarang).
   - **403 setelah ada 200** → **bukan** `auth_blocked`. Catat sebagai `rate_limited` dan beri jeda memakai pemutus bersama (jeda = `cooldown_seconds` profil jaringan B3). Setelah jeda habis, Coverr boleh dicoba lagi. Bila 403 terjadi 3× berturut-turut setelah jeda, barulah jeda dipakai untuk sisa run (tetap direset saat key berubah atau aplikasi restart).
3. Catat potongan isi respons 403 yang sudah diredaksi (maks. 200 karakter) ke log dan ke `source_status.coverr.last_error`, supaya penyebabnya bisa kita lihat lain kali.
4. Cek dokumentasi resmi Coverr API (api.coverr.co/docs) soal rate limit dan arti 403. Tulis temuan di Final Report: URL + kutipan maks. 15 kata + waktu akses, atau "tidak terverifikasi".
5. Pesan B2 dibedakan (id + en): `auth_blocked` → "Coverr dilewati: API key ditolak (401/403). Cek key di API & Penyedia AI."; `rate_limited` → "Coverr dijeda sementara: batas pemakaian (403) tercapai."
6. Tes: (a) 403 pada request pertama → `auth_blocked`, 0 request susulan; (b) 200, 200, lalu 403 → `rate_limited`, bukan `auth_blocked`, dan setelah jeda (waktu di-mock) Coverr dipanggil lagi; (c) peringatan UI memakai teks yang benar untuk masing-masing.
